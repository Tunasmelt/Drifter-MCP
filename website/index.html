Your agent's tools will change.

Drifter is a proxy on the MCP connection between your agent and its tools. It records real tool-use trajectories, then replays them against a deliberately mutated interface, so you can see whether your agent still gets the job done. No live calls under a mutated schema, no API cost per replayed call.

THE PROBLEM

MCP tools change under agents, silently.

Existing tools test models, servers, or agents in general. Nobody tests your actual agent against your actual tools under controlled interface change. Drifter fills that gap.

54.6%
of tools modified or deprecated across 515 MCP servers in a three-month study.
13.7–14.4%
degradation in frontier models under simulated tool evolution, concentrated in planning and reasoning, not call syntax.
12 mo
deprecation policy in the MCP spec itself, which guarantees the churn continues.
HOW IT WORKS

Record once. Replay against a changed interface.

RECORD · drifter observe
agent──MCP──▶drifter──MCP──▶real server

Real server, real traffic, recorded locally.

REPLAY + MUTATE · drifter run
agent──MCP──▶drifter (replayed, mutated)

No upstream server is contacted. A live call under a mutated schema never happens.

  1. 1
    Record
    drifter observe

    A transparent proxy writes each trajectory to a local JSONL corpus: which tools, in what order, with what arguments, and the shape of each result. Secret-looking strings are redacted.

  2. 2
    Mine (optional)
    drifter tasks mine

    Recurring workflows become editable task candidates with their evidence. You write the prompt and approve. Reads recordings only, so it costs nothing.

  3. 3
    Replay
    drifter replay-serve

    Recordings become an offline stand-in for the server. Unrecorded calls MISS, low-fidelity runs are excluded, and too few survivors means UNKNOWN.

  4. 4
    Mutate
    drifter run --operator …

    One structural, closed-set operator changes the tool interface the agent sees.

  5. 5
    Evaluate
    drifter run · drifter report

    The same task runs against unmutated and mutated manifests. Drifter compares behavior, checks assertions and screens for safety.

MUTATIONS

Three structural operators, all closed-set.

No free-text generation anywhere. Every operator's output space is fixed and reviewable as data.

Renames one input parameter, snake_case to camelCase. Drifter still recognises the resulting call through inverse-mutation key resolution, so replay keeps working even though the schema changed.

CHANGES
One input parameter’s name in one tool’s schema.
NEVER CHANGES
Tool names, other parameters, other tools.

VERDICTS

Three axes. Honest about what it doesn't know.

Every verdict defaults to UNKNOWN when there isn't enough evidence. Drifter would rather say it doesn't know than show a plausible-looking wrong answer.

Behaviorexperimental

How often the agent stays on the path your recordings established, before and after mutation, under a pre-registered interval rule. Below a minimum of valid runs per arm: UNKNOWN, with counts.

Taskopt-in

Assertions you author: tools that must be called, in what order, which must not be, and an answer_matches oracle on the final answer. None configured: UNKNOWN, never PASS.

Safetyalways on

Evaluated on every run, never gated by the others. Destructive calls are flagged; calls it couldn't classify are reported explicitly. Set policy.max_risk to cap risk.

Exit codes for CI
0Clean
1Behavior regression
2Assertion failure
3Safety violation
4Config / connectivity
5Budget exceeded
GET STARTED

From install to first report.

1 · Install and set up
uv tool install mcp-drifter
drifter init      # finds servers in .mcp.json, Cursor, Claude Desktop
drifter doctor    # config, connectivity, tool risk
2 · Record real sessions
drifter observe --server my-server
# point your agent’s MCP config at this,
# then use it normally
3 · Mine tasks (optional)
drifter tasks mine
# write each prompt in task_candidates.yaml
drifter tasks approve <id>
4 · Check coverage, then run
drifter coverage --server my-server
drifter run --fixture .drifter/runs --server my-server \
  --task-id my-task --operator parameter_rename --yes
drifter report --task-id my-task

STATUS AND LIMITS

Alpha, and upfront about it.

What is solid
  • Recording, replay, scoring and safety checks, exercised end to end.
  • No telemetry. Recordings stay on your machine; secret-looking strings are redacted before writing.
  • A mutated call is never forwarded to a live server.
  • Tested on Python 3.11–3.13, over stdio and HTTP, both MCP protocol eras.
What to keep in mind
  • Replay serves recorded response shapes; content-dependent tasks need an authored --response-fixture.
  • A real agent explores, so one recording rarely covers the next run. Check coverage first.
  • Detecting a genuine regression with a real agent is not yet separately validated. Don't use Behavior verdicts for release decisions.
  • Keep .drifter/ out of git. Expect the interface to change pre-1.0.
